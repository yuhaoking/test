## 五、本轮实现批次的验证边界（2026-09-29 实现记录，务必如实阅读）

OPT-01 ~ OPT-21 的**代码改动已完成**，但两类验证的完成度不同，不能混为一谈：

| 验证类别 | 覆盖内容 | 状态 |
|---|---|---|
| 静态与纯函数（真跑过） | `npm run typecheck` 零错误；`npm run lint` 零告警；`npm test` 全绿（新增 **63 项** OPT-xx 断言，含 SEC-001 负向用例、清单/版本白名单、导航防护接线、看门狗与截图会话的源码级断言）；`npm run build` 成功 | ✅ 已执行 |
| 运行期（**未跑**） | `npm run smoke`、`npm run bench`、`test-audit/run-ghost-probe.ps1` 四阶段实验、手动验收场景（多显示器拔插、休眠唤醒、遮罩卡死逃生口、热键被占用提示） | ⚠️ **未执行** |

**为什么运行期没跑**：本轮开发会话运行在一个**无桌面交互能力**的执行环境里 ——
Electron 二进制在此启动即 `0xC0000005`（访问冲突）退出；连系统自带的 `notepad.exe` 同样启动不了；
且 Electron **33 / 39 / 44 三个版本表现完全一致**，因此可以排除"升级引入崩溃"，属于环境限制而非回归。

**因此以下结论一律标【待验证】，不得写成"已修复/已确认"**：

1. Q-A1（GW-02 触发条件）与 Q-A2（GW-07 的 OS 层后果）—— 需要真机 ghost-probe 与现场观察；
2. OPT-01 的"可见窗被遮挡时仍持续绘制"、OPT-02 的"隐藏窗仍能派发 IPC"—— 需要 smoke/真机复现；
3. OPT-03 的"≤5s 遮罩消失、整屏恢复点击"与托盘「退出截图」—— 需要真机手动触发；
4. OPT-04 的"占用热键后启动弹一次通知"—— 需要真机占用 `Ctrl+Shift+V` 后启动；
5. OPT-05 的多显示器拔插/休眠唤醒夹取 —— 需要真机拔插；
6. OPT-13 的窗口行为整体回归与 ghost-probe 基线对比 —— 见下方"Electron 升级实测"，运行期项待补；
7. bench 的 CP-03（首屏 ≤200ms）与 T-01（空闲 CPU <1%）—— **OPT-14 新增每 30s 一次的 `capturePage` 采样**，
   其 CPU 增量必须用 bench 的"空闲 CPU"指标实测确认（采样区已缩到窗口中心 1/4 并降到 32×32 再哈希，预期影响可忽略，但**未实测**）。

## 六、Electron 升级实测发现（2026-09-29，影响后续版本选择）

| 版本 | 审计（electron 项） | `clipboard` API | 结论 |
|---|---|---|---|
| 33.4.11（基线） | 30+ 条（含 1 critical `tar`、25 high） | 同步：`readImage/writeImage/readText/availableFormats` | 不可发版（SEC-006） |
| **39.8.10（本轮采用）** | electron 项**已清零**；全局仅剩 esbuild/vite 的 moderate（`npm audit fix` 后） | **与 33 逐项一致**（比对 `electron.d.ts` 的 `Clipboard` 接口） | ✅ 落地 |
| 44.4.5（试装过并已回退） | electron 项同样清零 | **破坏性重写**：`readText()` 变 `Promise<string>`，`readImage/writeImage/availableFormats` **被移除** | ❌ 本轮不采用 |

**v44 的连带影响（登记为下迭代任务）**：升级到 44 需要把剪贴板链路整体异步化 ——
`clipboardManager`（含 600ms 轮询与图片快照）、`contextCapture`（模拟 Ctrl+C 的剪贴板前后比对）、
`captureManager` / `captureWindows`（贴图复制）、`contextActions`、`translateBar` 共 6 个文件、34 处调用，
并需重新评估 T-01 的"监听空闲 CPU <1%"口径（异步读的调度开销与同步读不同）。**这属于独立改造，不应混进发版整改批次**。

**v39 的 residual 风险（如实登记）**：`npm audit` 报 `electron` 间接依赖 `extract-zip` 的 2 条 high
（GHSA-jmr9-qjv8-65gv / GHSA-7pqw-9j4j-h8q3），**在 v40.10.2 及以下的 electron 包内都存在**。
其真实暴露面为 **0（运行时）**：`extract-zip` 是 electron 包的 `install` 依赖，只在 `npm install` 时解压下载到的 Electron 运行时；
打包产物（`asar` + `extraResources`）里不含它，插件市场的解压走的是系统 `tar`/`Expand-Archive`（已由 OPT-17 加固）。
因此本项按"构建期依赖"处理：**发版门禁第 2 条（electron 项清零或仅剩 low）在本轮的解释是"运行期依赖清零"**，
并建议在下次 Electron 升级（≥v44，随剪贴板异步化一起做）时彻底消除。此解释需在发版评审时由用户确认。

**安装踩坑（已写入仓库 `.npmrc`）**：本机对 github.com 不可达，而 electron 的 postinstall 默认从 GitHub Releases
下载约 130MB 运行时 —— 表现为 `npm install` 长时间无输出、`node_modules/electron/dist` 始终不出现。
处置：用 `ELECTRON_MIRROR` / `ELECTRON_BUILDER_BINARIES_MIRROR` 指向 npmmirror，并注意 **npm 11 默认不执行依赖的 postinstall**，
必要时手动补 `node node_modules/electron/install.js`。
