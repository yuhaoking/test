# 优化方案决策日志（ADR，v1.1）

> 版本：v1.1（2026-09-29）｜上游：`docs/优化方案-总览.md`
> 记录本优化方案的关键决策：背景 → 备选 → 结论 → 理由 → 被否决项。被否决的方案也记录，避免日后翻案时重复论证。

## ADR-01 批次策略：混合热修批次

- **背景**：安全审计按"发版门禁"排优先级（阻断项第一），幽灵窗口分析按"用户正在被折磨"排（GW-02 第一）；两者都动 `electron/windows/` 公共层，混做无法归因回归。
- **备选**：A 混合热修批次（批次 1 = 幽灵窗口低成本项 + SEC-001/002，批次 2 = Electron 升级等大项）；B 幽灵窗口先行；C 安全阻断项先行；D 两条线并行。
- **结论**：**A**。
- **理由**：小改动集中释放，一次回归同时改善体感与安全；批次 2 单独动版本，回归归因清晰；单人开发（默认）下 D 不现实。
- **否决**：B 会把 SEC-001（数据销毁链）多留一批；C 会让"点不动"继续折磨用户；D 需要两份人力且要维护两套回归。

## ADR-02 发布形态：面向公众分发

- **背景**：审计假设台账第 1 条标注"发布形态仅假设，会翻转 SEC-006 门禁措辞"。
- **结论**：**面向公众分发**。
- **理由**：用户拍板。推论：SEC-006 门禁保持"依赖 High CVE 即 No-Go"最严措辞；市场信任链（SEC-004/005）不能空转；V-4 代码签名判"需要"。
- **影响**：写入发版门禁 6 条；SEC-004/005 从"可带病上线"升级为"发版前必须最小闭环"（OPT-15/16）。

## ADR-03 Electron 升级时机：批次 2 就升

- **背景**：33.4.11 带 30+ 已知漏洞（含 context isolation 绕过），跨 3 个大版本升级是 L 级工作量，升级可能改变窗口/节流默认行为。
- **备选**：A 批次 2 就升；B 幽灵窗口跑稳 1~2 周再升；C 暂不升级只登记。
- **结论**：**A**。
- **理由**：审计口径"修复 Critical+High 后可上线"中 SEC-006 是阻断项；拖越久 CVE 暴露窗口越长，且 SEC-002 的利用难度会被老版本再降一档；批次 2 升级后整体回归一次即可。
- **否决**：B 归因更清晰但漏洞多留数周；C 与 ADR-02 公众分发直接冲突。
- **风险对冲**：OPT-R1——批次 1 只用稳定 API，升级后重跑 ghost-probe 对比基线。

## ADR-04 市场信任链：先关远程索引，签名制排批次 3

- **背景**：verified 由索引自报（等于没有信任根），同 id 可顶替内置插件；完整签名体系（T-05）是 L 级。
- **备选**：A 直接做签名体系；B 先关远程索引只用内置源，签名制下迭代；C 不动。
- **结论**：**B**（先关远程索引），签名制排批次 3。
- **理由**：关闭远程索引是 S 级改动，立刻把供应链攻击面收敛到"内置源 + 用户主动安装"；签名体系值得做但不该挡发版。
- **硬约束（防翻案）**：**T-05 签名制完成前，远程索引不得恢复默认开启**（发版门禁第 5 条 + 风险 OPT-R4）；"✅ 官方验证"文案在签名落地前必须如实化（OPT-16）。
- **否决**：A 周期长挡发版；C 在"面向公众分发"（ADR-02）下不可接受。

## ADR-05 FUN-001 加密留存：先改文案

- **背景**："安装包加密留存，可离线重装"承诺了但全仓无还原入口（数据可保全但不可用）。
- **备选**：A 补离线重装功能；B 改文案为"仅加密归档"；C 文案现在改、功能排期。
- **结论**：**B 止血**，"离线重装"作为独立需求登记批次 3（效果等价于 C 的前半段，功能是否做留到批次 3 立项时再议）。
- **理由**：S 级改动立刻消除名实不符；功能是 M 级，不该挡本轮两批主线。
- **否决**：A 本轮资源应给幽灵窗口与阻断项。

## ADR-06 任务编号改用 OPT-xx

- **背景**：审计文档的任务编号 T-01~T-15 与既有 `tasks.md` 的 T-01~T-14 **重名不同义**（如两边的"T-03"分别是 Electron 升级和系统整合收尾）。
- **结论**：本方案任务一律 **OPT-xx**，映射表见 `docs/优化方案-tasks.md` 附录 A；`tasks.md` 既有清单不动。
- **理由**：开发/验收沟通零歧义；历史文档不需要改写（增量原则）。
