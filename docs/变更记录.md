## 2026-09-30 — RUN-001 关键澄清：此前所有"正常"运行都是被强制提权的，沙箱从未被真正测过

| 项 | 内容 |
|----|------|
| **决定性发现** | 字节级读取 `.lnk`：`② 兼容模式（关闭沙箱）.lnk` 的 LinkFlags 含 **`RunAsUser`(0x20) = 以管理员身份运行**。也就是说该快捷方式**强制提权** —— 而提权路径会**绕过 SmartScreen**，所以它"能启动"；`① 普通启动（沙箱开启）.lnk` 不带提权 → 被 SmartScreen 拦截 → "没页面"。**"① 失败"并不是沙箱失败，而是根本没启动。** |
| **由此推翻的结论** | 先前"沙箱开启 = 失败"的对照是**被污染的**：所有能跑到应用里的运行都是提权运行（`提权运行=是`），从未有过一次"非提权 + 沙箱开启"的真实样本。 |
| **已排除（本轮新增）** | ① 应用代码无任何提权调用（仅 `app.relaunch`，继承当前权限）；② 全域搜索 `RUNASADMIN`：HKCU/HKLM 中**没有本程序条目**（只有模拟器与考试程序）；③ UAC 配置正常（`EnableLUA=1`、`ConsentPromptBehaviorAdmin=5`）；④ 会话本身是 `Medium` 完整性（未提权）。**结论：提权来自启动链而非应用或系统策略，具体来源仍未定位。** |
| **发现的真实缺陷（用户侧，需清理）** | `HKCU\...\CurrentVersion\Run` 有**两条**自启项：`com.xiaopeng.toolbox` → 当前路径（有效）；`electron.app.Electron` → `D:\小鹏工具箱\...`（**路径已不存在**，是失败的旧安装残留）。后者会导致每次开机静默失败一次。 |
| **处置（按证据，不预测）** | 新增**反应式**恢复：默认**保持沙箱开启**；只有真的观测到 `render-process-gone(reason=launch-failed)` 且沙箱处于开启状态时，才自动以 `--no-sandbox` 重启**一次**（带防循环标志），并在日志写明原因。若已关沙箱仍失败，则明确记录"问题不在沙箱"且不再徒劳重启。**与之前被撤掉的"预测式降级"的本质区别**：预测式在没有任何失败证据时就先关沙箱，污染了全部观测数据；反应式只在**实测到沙箱初始化失败**后恢复，且有据可查。 |

## 2026-09-30 — RUN-001 结案：根因是 Nahimic 的 DLL 注入（非提权、非沙箱）

| 项 | 内容 |
|----|------|
| **根因（已实测确认）** | **Nahimic 音效软件把 DLL 注入到 Chromium 进程**，导致应用在 **JS 执行之前**的原生初始化阶段就崩溃。取证：①最小探针（`MinProbe.exe`，仅一行代码、与我们业务代码无关）同样启动即崩 —— `Exception code: 0x80000003, Fault offset: 0x68cf3db`，`Faulting module = MinProbe.exe` 自身；②`electron.exe --version` 正常（该路径不初始化 Chromium）；③本机 `NahimicService` 正在运行，`C:\Windows\System32` 下有整套注入 DLL（`NahimicAPO4.dll` 7MB 等）与内核驱动 `Nahimic_Mirroring.sys`。**停用 NahimicService 后应用正常**：`启动自检：6 个窗口渲染进程正常`、`launch-failed` 归零。 |
| **此前两次误判（如实更正）** | ①"Electron 33→39 回归" —— 被证伪：两版表现一致；②"提权导致渲染子进程建不了" —— **判断过头**：停用 Nahimic 后**提权状态下 6 个窗口也全部正常**。提权只是当时唯一能绕过 SmartScreen 的启动路径，与根因无关。 |
| **修复（应用侧能做与不能做）** | 崩溃发生在我们的代码运行之前，**应用层无法自愈**。因此交付：①把该环境冲突写进文档与已知问题；②保留"渲染异常探针"（默认零噪音，只在异常时写 `render-probe.log`，256KB 上限）以便下次快速定性；③提权自动降级沙箱保留（对沙箱受限环境仍有价值，但不再是根因对策）。 |
