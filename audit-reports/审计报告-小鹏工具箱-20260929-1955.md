## 二、P0 安全问题（必须先修）

### [SEC-001] 插件目录安装用未校验的 manifest.id 拼路径，可递归删除任意目录（含整个 userData）
- **严重度**：High
- **类别**：配置与暴露面（路径穿越 / 任意目录删除）
- **位置**：electron/services/pluginManager.ts:905-909（根因：readManifest 不校验 id，electron/services/pluginManager.ts:98-107）
- **证据**：
  ```typescript
  const manifest = readManifest(dir);
  if (!manifest) throw new Error('所选目录不是有效插件（缺少 manifest.json）');
  const target = join(parent, manifest.id);
  if (existsSync(target)) rmSync(target, { recursive: true, force: true });
  cpSync(dir, target, { recursive: true });
  ```
  其中 readManifest 只查字段存在性：`if (!m.id || !m.name || !m.entry) return null;`（pluginManager.ts:102），对 id 无任何格式/类型校验。
- **风险链**：用户在「安装插件」目录选择框（PluginStoreView.vue:91 → plugins:install → installPlugin，pluginManager.ts:896-913）里选中一个恶意插件目录 → 其 manifest.json 写 `"id": ".."` → `join(userData\plugins, '..')` 归一化为 userData 本身 → `rmSync(userData, {recursive:true, force:true})` 递归删除用户全部数据（xiaopeng-v2.db 数据库、剪贴板历史与加密图片、.secret.key 密钥、主题包、设置），随后把攻击者目录内容复制到该位置。
- **自查**：（1）考虑过"用户自己选的目录算不算攻击面"——算：UI 语义是"安装插件"，用户预期绝不是"删掉我的数据目录"，且插件常由他人分享；（2）考虑过 join 是否真的归一化 `..` 段——path.join 逐段拼接并归一化，`join('C:\\u\\plugins','..') === 'C:\\u'`，逃逸成立；（3）考虑过别处是否已拦——跑了 `grep assertPluginId|PLUGIN_ID_RE pluginManager.ts` 无命中，而 marketplace.ts:421/454 与 pluginForge.ts:141-154 同类入口都做了 id 白名单校验，唯独本入口缺失，排除"重复防护误报"；（4）考虑过 rmSync 是否真的到手就删——existsSync(target) 为 true 时先删后拷，无二次确认对话框（对比 loadPlugin 有确认弹窗）。
- **修复方向**：
  1. installPlugin 里 readManifest 之后立即 `assertPluginId(manifest.id)`（可直接复用 marketplace.ts:30-32 的 PLUGIN_ID_RE），并加 containment 断言 `target.startsWith(parent + sep)`（同 marketplace.ts:473-477 的写法）。
  2. 删除已有目录前弹确认框（复用 loadPlugin 的 dialog 模式），并在 rmSync 前断言 target 位于 plugins 根内。
- **同类位置**：electron/services/pluginForge.ts 的 installGenerated 已有等价校验（163-190），可作参照实现。

### [SEC-002] 全局缺失 setWindowOpenHandler / will-navigate 防护，外链可进入持有全量 IPC 的窗口
- **严重度**：High（利用链后半段 preload 继承细节标注【待验证】，见自查）
- **类别**：配置与暴露面（Electron 安全基线）
- **位置**：src/components/TodoList.vue:273-276（渲染 target=_blank 外链）；缺失点：electron/windows/common.ts:46-54（loadPage 统一入口，未挂任何导航守卫）
- **证据**：
  ```typescript
  // TodoList.vue:273-276（mdToHtml 输出，v-html 渲染到 .md-preview）
  .replace(
    /[([^]]+)]((https?://[^s)"'&<>]+))/g,
    '<a href="$2" target="_blank" rel="noopener noreferrer">$1</a>'
  )
  ```
  只读扫描证据：`grep -n "setWindowOpenHandler|will-navigate|will-attach-webview" electron/` **零命中**（全仓仅 test-audit/scripts 的测试夹具里有 webContents.on('console-message') 之类）。
- **风险链**：待办备注里粘进一段带 markdown 链接的文本（来自网页/剪贴板）→ 用户在预览里点一下链接 → Electron 默认行为是新开 BrowserWindow 而非系统浏览器，子窗口继承父窗口 webPreferences（含 preload）→ 远程页面获得 `window.api` → 经 `servers:launch`（serverLauncher.ts:67-113，argv 形式 spawn 任意程序）、`files:open`、`plugins:install`、`store:update-settings`（可写 trustedSources）等通道在本机执行任意操作。即使继承细节不成立，"应用内窗口加载远程页面"本身也越过了"只加载本地内容"的信任边界（common.ts:52 的 loadFile 是全部窗口的唯一加载方式）。
- **自查**：（1）考虑过 mdToHtml 是否已把 XSS 堵死从而无触发面——已堵（258-277 先转义 `& < > " '`，URL 类字符集受限），但 `target="_blank"` 的合法外链本身就是触发点，不需要 XSS；（2）考虑过 Electron 是否默认用系统浏览器打开 target=_blank——不是，默认创建新 BrowserWindow，除非 setWindowOpenHandler 拦截；（3）**子窗口是否真的继承 preload 并暴露 window.api，本轮未做运行时 PoC，标注【待验证】**——但防护缺失这一事实由 grep 零命中直接证实，且补防护成本极低，无论继承与否都应修；（4）考虑过 ChatApp 等其他渲染面——LLM 回复用 `{{ m.content }}` 文本插值（ChatApp.vue:122），无第二处 v-html，故同类位置只有 TodoList 一处。
- **修复方向**：
  1. 在窗口创建统一入口（windows/common.ts loadPage 或各 window 工厂）注册 `win.webContents.setWindowOpenHandler(() => ({ action: 'deny' }))` + 需要开外链的场景改调 openExternalSafe（electron/utils/openExternalSafe.ts:9，已有 http/https/mailto 白名单）。
  2. 注册 `win.webContents.on('will-navigate', (e, url) => { e.preventDefault(); void openExternalSafe(url); })`。
- **同类位置**：TodoList.vue:273 是唯一 v-html 渲染面；15 个窗口（windows/*.ts）均未挂守卫。

### [SEC-003] 用户的 DeepSeek API Key 与全部环境变量注入每个插件子进程
- **严重度**：Medium
- **类别**：敏感信息泄漏
- **位置**：electron/services/pluginManager.ts:341-347
- **证据**：
  ```typescript
  child = spawn(resolvePython(), [entry], {
    cwd: runtime.dir,
    windowsHide: true,
    stdio: ['pipe', 'pipe', 'pipe'],
    env: {
      ...process.env,
      PYTHONUTF8: '1',
      PLUGIN_SAVE_DIR: dataStore().get().settings.saveDir || '',
      ENGINES_ROOT: enginesDir(),
      DEEPSEEK_API_KEY: dataStore().get().settings.deepseekApiKey || ''
    }
  });
  ```
- **风险链**：任何插件子进程（包括仅在确认框点过一次"确认加载"的第三方市场插件）用 `os.environ['DEEPSEEK_API_KEY']` 即可读走用户 API Key 并外传——不需要 manifest.permissions、不需要额外文件读写痕迹。授权确认框（pluginManager.ts:701-710）只说"插件将运行本地代码"，未披露会把 API Key 交给它。
- **自查**：（1）考虑过"插件本就能执行任意代码，泄漏密钥是不是增量风险"——是增量：拿密钥只需一次环境变量读取，隐蔽性远高于明文外传行为，且密钥价值（计费额度）独立于本机权限；（2）考虑过是否只有内置翻译/监控插件需要该变量——office-translate-pro/office-deepseek-monitor 确实使用（plugins/*/main.py），但 spawn 处对所有插件一视同仁，无按插件白名单放行；（3）考虑过 manifest.permissions 是否能裁剪 env——permissions 仅用于展示（marketplace.ts:390-399、pluginForge.ts:204），spawn 侧无任何按权限过滤逻辑（全文件已读完）。
- **修复方向**：
  1. DEEPSEEK_API_KEY 改为按插件显式声明（如 manifest.permissions 含 'network' 且 id 在白名单）才注入，或改为宿主代发请求（插件走 JSON-RPC 让宿主调 LLM），插件进程永远见不到密钥。
  2. 授权弹窗 detail 中补一行"该插件将获得：API Key 使用权 / 保存目录 / 环境变量"。
- **同类位置**：`...process.env` 全量透传属同类问题（插件同时拿到宿主所有环境变量）。

### [SEC-004] 插件市场信任根弱："✅ 官方验证"由索引自报，装完自动信任 + 自动 pip + 自动加载
- **严重度**：Medium
- **类别**：配置与暴露面（供应链）
- **位置**：electron/services/marketplace.ts:401（verified 自报展示）、marketplace.ts:485-498（自动信任/加载）、marketplace.ts:242-247（SHA256 与包同信道）
- **证据**：
  ```typescript
  item.verified === true ? '✅ 官方验证：已通过' : '⚠️ “社区未验证”标签：该插件未经官方验证，请自行确认来源可信',
  ...
  // 权限提示已在确认对话框完成：标记为信任来源，加载时不再二次弹窗
  if (!s.trustedSources.includes(manifest.id)) {
    dataStore().updateSettings({ trustedSources: [...s.trustedSources, manifest.id] });
  }
  await loadPlugin(manifest.id);   // 一键启用：加载并自动解析 requirements.txt（复用现有自动 pip 机制）
  ```
- **风险链**：用户配置/默认的市场索引一旦被投毒（或第三方索引源恶意），索引条目自带 `"verified": true` 即可让确认框显示"✅ 官方验证：已通过" → 用户据此信任并点安装 → 包自动解压、自动写入 trustedSources（此后永不弹窗）、自动 pip install 其 requirements.txt（联网拉包、含 setup 执行）、自动 spawn 执行 Python。SHA256 校验（242-247）只防传输篡改，索引与包同信道，防不了源投毒；全仓无签名/公钥固定（grep minisign|signature|publicKey 零命中）。
- **自查**：（1）考虑过 verified 是否来自可信白名单——parseIndex（117-128）只校验 id/name/url 三个字段，verified 是攻击者可控布尔值，排除；（2）考虑过确认框是否如实披露风险——披露了"将运行本地代码并自动安装 requirements.txt 依赖"（402 行），故不算隐瞒，但"官方验证"字样是错误背书，属声明与实现不符；（3）考虑过 SHA256 能否替代签名——不能，两者同源，已排除"已有哈希即安全"的误判。
- **修复方向**：
  1. `verified` 改为随索引分发的签名（Ed25519/minisign，公钥内置在应用里），UI 只在验签通过时显示"官方验证"；验不过一律显示"社区未验证"。
  2. 自动写 trustedSources 改为"安装后首次加载仍弹一次窗"，或至少在 detail 里明示"安装即永久信任该 id"。
- **同类位置**：pluginForge.ts:224 生成插件也按 id 直接写 trustedSources（同样无内容绑定）。

### [SEC-005] 市场条目可用同名 id 顶替内置插件（market:upgrade 绕过"已安装"门 + userData 目录优先扫描）
- **严重度**：Medium
- **类别**：鉴权与信任模型（命名空间冲突）
- **位置**：electron/services/marketplace.ts:453-457（upgrade 跳过已安装检查）、marketplace.ts:471-484（落到 userData/plugins/<id>）、electron/store/dataStore.ts:540-545（pluginsDirs：userData 排在内置目录之前）
- **证据**：
  ```typescript
  if (!upgrade && listPlugins().some((p) => p.id === item.id)) {
    throw new Error(`插件“${item.name}”已安装，可使用“更新”`);
  }
  ...
  const target = resolve(pluginsRoot, manifest.id);   // pluginsRoot = userData\plugins
  rmSync(target, { recursive: true, force: true });
  ```
  内置插件 id 实测即反向域名式（plugins/office-screenshot-region/manifest.json:2 `"id": "com.office.screenshot.region"`），可通过 PLUGIN_ID_RE（marketplace.ts:28）。
- **风险链**：恶意索引发布 id=`com.office.screenshot.region` 的条目 → 用户点"更新"→ 确认框显示"更新插件…✅ 官方验证"→ 包写入 userData\plugins\com.office.screenshot.region → pluginsDirs() 里 userData 在前（dataStore.ts:540-544），listPlugins 用 `store.plugins.find`/目录顺序取到的都是市场副本 → 内置截图插件被静默替换执行（且 status='user'、trustedSources 已含该 id，此后零弹窗）。

### [SEC-008] 插件市场解压前校验 fail-open 且校验器与解压器不一致，解压无总量/条目/压缩比上限
- **严重度**：Low（安装包已被用户确认框授权，且包内代码本会执行；此处的增量风险是"在代码运行前就写盘"）
- **类别**：配置与暴露面 / 输入校验
- **位置**：electron/services/marketplace.ts:311-318（fail-open）、332-359（tar 失败回退 Expand-Archive）、284-292（仅有下载侧 120MB 上限）
- **证据**：
  ```typescript
  execFile('tar', ['-tf', zip], {...}, (err, stdout) => {
    if (err) return resolve([]); // 列目录失败时不阻断（解压阶段仍会失败并提示）
    resolve(String(stdout).split(/\r?\n/));
  });
  ...
  execFile('tar', ['-xf', zip, '-C', dest], {...}, (err) => {
    if (!err) return resolve();
    execFile('powershell.exe', [..., `Expand-Archive -LiteralPath '${zip.replace(/'/g, "''")}' ...`], ...)
  ```
- **风险链**：`tar -tf` 失败被当"0 条目"放行 → assertZipSafe([]) 空转通过 → 随后若 `tar -xf` 也失败而 PowerShell Expand-Archive 成功（两者对畸形 ZIP 的宽容度不同），zip-slip 校验等于没做，恶意包可在解压阶段写出 staging 之外的文件；另外 120MB 压缩包可解出远超体积的内容（对比 shared/themePack/zip.ts:37-43 有 512 条目/64MB 总量/200 压缩比护栏，市场链路没有）。
- **自查**：（1）考虑过 tar -tf 失败时 tar -xf 是否必然失败——不必然，代码注释自己承认存在"tar 失败回退 PowerShell"路径，反驳失败，故 fail-open 判定成立；（2）考虑过能否构造出实际穿越——本轮未做 PoC，标注【待验证】，故定级 Low 而非 High；（3）考虑过 zip 炸弹的现实影响——安装已过用户确认，且同一包可直接执行代码，增量有限，归 Low。
- **修复方向**：`if (err) return reject(...)`（fail-closed）；统一用同一解析器做校验与解压（或解压后再断言落盘文件全部在 dest 内）；补总量/条目数/压缩比上限（直接复用 themePack 的 DEFAULT_ZIP_LIMITS）。
- **同类位置**：shared/themePack/zip.ts 的实现可作正确参照（119-136 normalizeZipPath 全面拦截穿越/ADS/设备名）。

## 四、P1 功能缺陷与健壮性

### [DEF-001] readManifest 不校验字段类型，畸形 manifest 会让插件列表整体抛错
- **严重度**：Medium
- **位置**：electron/services/pluginManager.ts:98-107（构造）与 :169（抛点）
- **证据**：readManifest 只查 `if (!m.id || !m.name || !m.entry) return null;`；listPlugins 内 `icon: manifest.icon ? join(full, manifest.icon) : undefined`（169 行）——icon 为数字/对象时 path.join 抛 TypeError，而 152-156 的 try 只包 existsSync。
- **触发条件**：任意插件目录（含用户安装、市场包）内 manifest.json 的 icon/name/entry 为非字符串 JSON 类型。
- **后果**：listPlugins() 整体 throw → plugins:list 对所有窗口失败 → 插件面板全挂（且广播 plugins:changed 同步失败）。
- **自查**：考虑过 readManifest 的 try/catch 是否已兜住——它只兜 readFileSync/JSON.parse/字段存在性，join 在调用方，排除误报。
- **修复方向**：readManifest 内逐字段做 `String()` 归一 + 长度上限（参照 pluginForge.ts:163-177 的 safeRelativeFileName/safeVersion）。

### [DEF-002] 主题扫描遇非法目录名直接 throw，主题功能整体不可用
- **严重度**：Medium
- **位置**：electron/services/themePack.ts:70-73（themeDir 校验即抛）、:101-103（抛点在 try 之外）、:215（scanThemes 未兜）
- **证据**：
  ```typescript
  function readInstalledManifest(id: string): ThemeManifest | null {
    const file = join(themeDir(id), THEME_ENTRY);   // ← themeDir 对非法 id throw，位于 try 之前
    if (!existsSync(file)) return null;
    try { ... }
  ```
  scanThemes 对 themes/ 下每个目录名调用 readInstalledManifest(n)（215 行），仅跳过 '.' 开头（208 行）。
- **触发条件**：themes/ 目录下出现任何不满足 isValidThemeId 的目录（用户手动备份的"旧主题"、第三方同步盘生成的目录等）。
- **后果**：listThemes() 全量抛错 → 主题列表/应用/校验/导出全部失效。
- **自查**：考虑过 statSync 那层 try 是否覆盖——207-214 只覆盖 statSync，themeDir 在 102 行位于 try(104) 之前，排除误报。
- **修复方向**：readInstalledManifest 入口先 `if (!isValidThemeId(id)) return null;`；scanThemes 的单目录处理包 try/catch。

### [DEF-003] 插件 stdout 行缓冲无上限，无换行巨行耗尽主进程内存
- **严重度**：Medium
- **位置**：electron/services/pluginManager.ts:363-370
- **证据**：`runtime.buffer += chunk` 循环找 `\n`，无长度上限、无背压（对比 376 行 stderr 有 2KB 截断）。
- **触发条件**：插件输出不带换行的持续数据或单条超大 JSON 行。
- **后果**：主进程内存持续增长 → 全部窗口卡死/OOM（主进程崩溃 = 所有功能消失）。
- **自查**：grep `maxBuffer|buffer.length|slice(-` 全文件仅 stderr 截断一处，排除"已有上限"误报。
- **修复方向**：buffer 超过阈值（如 1MB）即截断并标记该插件为 error；或对超长行直接 kill 子进程。

### [DEF-004] 插件可自续保护窗口且 jobs 无上限，进程可永不回收
- **严重度**：Low
- **位置**：electron/services/pluginManager.ts:935-953（busyUntil 由消息文本解析秒数、无 clamp）、:417-459（jobs Map 无界）、:561-570（插件主动上报 job）
- **证据**：`const span = sec ? Number(sec[1]) * 1000 + BACKGROUND_MARGIN_MS : ...`（941-947）——插件返回"录制中（999999 秒）"即获得约 11.5 天保护窗；job 事件可无限新增不同 jobId。
- **触发条件**：插件（或有缺陷的插件）持续上报 running 任务。
- **后果**：空闲回收器（1108-1134）永不生效，子进程常驻 + jobs Map 无界增长。
- **自查**：考虑过是否有数量上限——upsertJob/事件入口均无 clamp，排除误报；后果是资源占用非越权，定级 Low。
- **修复方向**：span clamp 到 ≤2h；jobs 数量上限（如 50）+ 定期清理首条即终态的任务。

### [DEF-005] 插件子进程 kill() 不杀进程树，孙进程在卸载/回收/退出后残留
- **严重度**：Low
- **位置**：electron/services/pluginManager.ts:853-858（同类 1052-1061、1123-1128）
- **证据**：`runtime.child?.kill()`；对比 serverLauncher.ts:118 用 `taskkill /pid <pid> /T /F` 杀进程树。
- **触发条件**：插件内用 subprocess 拉起 ffmpeg/转换器等子进程后被卸载或空闲回收。
- **后果**：孙进程残留继续占用 CPU/写盘，用户无法从 UI 终止。
- **自查**：grep services 下 taskkill/job.kill 仅 serverLauncher 用 /T，确认插件侧无进程树处理。
- **修复方向**：Windows 下统一用 taskkill /T /F（或 Job Object）终止插件进程树。

### [DEF-006] requirements.txt 原样交给 pip 解析，可注入 pip 选项（安装源劫持）
- **严重度**：Low（插件代码本可执行，纵深问题；但 pip 阶段可早于任何用户可见行为）
- **位置**：electron/services/pluginManager.ts:754-765（配合 :1037 ensurePlugin、:1089-1096 startEnabledPlugins 自动安装）
- **证据**：`spawn(resolvePython(), ['-m','pip','install','setuptools','wheel','-r', join(rec.dir,'requirements.txt'), ...])`——requirements.txt 为插件可控文件，pip 需求文件支持 `--index-url/--extra-index-url/--trusted-host/-e` 等选项。
- **触发条件**：含恶意 requirements.txt 的插件被加载/自愈重装。
- **后果**：安装源被引向攻击者服务器，pip 阶段执行任意包代码。
- **自查**：考虑过 loadPlugin 是否先弹窗——是（698-710 弹窗在 715 pip 之前），但 ensurePlugin/startEnabledPlugins 路径对已启用插件直接 pip，无弹窗，判定成立。
- **修复方向**：逐行校验 requirements（只允许 `name==version` 形态，拒绝以 `-` 开头的行）；或加 `--no-index --find-links` 受限源。

### [DEF-007] 市场索引 item.version 未校验即参与文件路径拼接
- **严重度**：Low
- **位置**：electron/services/marketplace.ts:78（拼点）、:120-128（parseIndex 只校验 id/name/url）
- **证据**：`const file = join(dir, `${item.id}-v${item.version}.zip.enc`);`——version 含 `\..` 段即可越出 secure-packages/ 写文件。
- **触发条件**：恶意索引 + 用户开启 marketEncryptPackages 并点安装。
- **后果**：可在 userData 外写入 `*.zip.enc` 文件（后缀固定，无法消除），属受限任意路径写。
- **自查**：考虑过 id 前缀是否阻断 `..` 段——id 由 PLUGIN_ID_RE 约束无分隔符，但 version 可以 `\..` 开头使后续段独立成段，穿越成立；考虑过危害上限——内容为加密包、后缀固定，定级 Low。
- **修复方向**：version 加 `^[0-9A-Za-z._-]{1,32}$` 白名单（与 safeVersion 一致）。

### [DEF-008] 下载重定向无次数上限，失败路径留残留文件
- **严重度**：Low
- **位置**：electron/services/marketplace.ts:271-274（递归无计数，对比 httpGetText:139 有 3 次上限）、:443-450（下载失败/解压失败无 finally 清理）
- **证据**：`if (status >= 300 && status < 400 && res.headers.location) { res.resume(); downloadZip(res.headers.location, dest, sha256).then(resolve, reject); }`
- **触发条件**：恶意服务器 302 自环；或下载/校验失败。
- **后果**：安装流程挂起直到超时；market-staging 内半包文件无界累积。
- **自查**：考虑过 out.on('error') 是否清理——只有 SHA 失败分支 rmSync(297)，其余路径残留，判定成立。
- **修复方向**：downloadZip 加 redirects 形参计数；stageItem 用 try/finally 统一清理 staging。
