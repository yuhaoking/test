## 一、结论摘要

### 上线判定：❌ 不建议上线

阻断项两条，任一存在即不可发版：
1. **发行物根本装不上**——dist/ 里的安装包是 NSIS 两遍构建的第一遍中间产物（无内嵌载荷），双击无法安装；
2. **装了也起不来**——主进程正常、但全部窗口的渲染进程启动失败（launch-failed），界面完全不显示，且产品内没有可用自救路径。

## 三、P0.5 功能完整性与可用性

### [PKG-001] 安装包是 NSIS 两遍构建的中间产物，无法安装（High · 发布阻断）

- **触发点**：用户双击 dist/小鹏工具箱 Setup 2.1.0.exe（README.md:70 与 docs/acceptance-checklist.md:3 都说这是要交付的安装包）。
- **因果链**：electron-builder 的 NSIS 目标是**两遍构建**——
  1. 第一遍以 BUILD_UNINSTALLER 编出「不含内嵌归档」的中间安装器（node_modules/app-builder-lib/out/targets/nsis/NsisTarget.js:562 注释原文："BUILD_UNINSTALLER: intermediate uninstaller build — no embedded archives."；:566-568 只对最终安装器做体积校验）；
  2. 接着**运行一次该安装器**导出卸载器（NsisTarget.js:374 wineVm.exec(installerPath, ...)，产物名见 :349）；
  3. 第二遍 makensis 才把应用载荷（extractAppPackage.nsh:73 的 File /oname=$PLUGINSDIR\app-64.7z）打进去，并**覆盖同名 OutFile**（NsisTarget.js:185）。
  本项目的打包在第 2 步中断（docs/变更记录.md:13 已如实记录："该 EXE 会挂住不返回。因此 dist/ 里留下了半成品（小鹏工具箱 Setup 2.1.0.exe 仅 0.2MB、xiaopeng-toolbox-2.1.0-x64.nsis.7z 196.9MB 数据包），**不可分发**"）。
- **二进制取证**：
  - dist/小鹏工具箱 Setup 2.1.0.exe = 169,016 字节，而应用载荷 xiaopeng-toolbox-2.1.0-x64.nsis.7z = 206,465,244 字节——一个 169KB 的文件不可能装下 206MB 载荷；
  - 7-Zip 21.07（node_modules/.7zip-bin-*/win/x64/7za.exe）对该文件列包：无 Path/Type 输出、Errors: 1 —— 它不被识别为任何安装器/归档，即**不含可提取的载荷**；
  - 同目录小鹏工具箱 Setup 2.1.0.__uninstaller.exe（158,999B）正是 NsisTarget.js:349 定义的中间卸载器命名（path.basename(installerPath,"exe") + "__uninstaller.exe"），反证构建确实走到"导出卸载器"那一步就断了。
- **具体后果**：用户拿 README 指认的那个安装包去装，必然失败或装不出任何东西 → 完整命中症状①。
- **修复方向**：在**交互桌面**（能弹 UAC、有 GUI 会话）重跑 npm run dist（package.json:20），只发布第二遍产出的最终安装器（体积约 206MB）；并在构建后加产物自检（见 R2-T2）。
- **自查**：（1）考虑过"169KB 是不是 nsis-web 网络安装器、靠同目录 7z 安装"——反驳：electron-builder.yml:39-41 的 target 是 nsis，且 NsisTarget.js:334-336 isWebInstaller 固定 false，排除；（2）考虑过"7-Zip 列不出是中文文件名导致"——反驳：同一命令、同样含中文的 (merged).exe 能正常列出 10470 个文件，排除工具/编码因素；（3）考虑过"文件可能被杀软截断"——反驳：文件时间戳与 docs/变更记录.md:13 记录的"半成品"描述一致（09-29 23:17:22），且体积吻合"仅 0.2MB"，排除截断。

### [PKG-002] 「(merged).exe」是手工拼接的未验证产物（Medium）

- **证据**：小鹏工具箱 Setup 2.1.0 (merged).exe = 206,634,260B = 169,016 + 206,465,244（与 stub、nsis.7z 之和**严格相等**）；其前 169,016 字节与 stub **逐字节相同**；7-Zip 打开它报 Type = 7z、Physical Size = 206,465,244（正是 .nsis.7z 的字节数）→ 把 stub 与 7z 原样拼接。对 node_modules 全量 grep「(merged)」命中 0（仅 typescript 的无关字面量）→ **electron-builder 不产出这个命名**。
- **后果**：dist/ 同时存在 169KB"Setup"、206MB"(merged)"、159KB"__uninstaller"三个 exe，没有任何标记说明哪个能用；README/验收清单都没有提到 (merged)。
- **【待验证】**：(merged).exe 能否真正安装出可用程序未实测（实测=在用户机器上真装一次，属改动系统的动作，本轮不擅自执行，见 R2-T1 验收标准）。

### [REL-001] 交付物版本漂移：安装器与 win-unpacked 不是同一个构建（Medium）

- **证据**：(merged).exe 内的应用 exe 解压后为 210,896,896B；当前 dist/win-unpacked/小鹏工具箱.exe 为 188,784,128B、FileVersion=33.4.11（时间戳 09-30 20:43:59）；dist/builder-effective-config.yaml 记录该次打包 electronVersion: 39.8.10（该文件时间戳 09-29 22:28:11）。即：**安装器里打的是 Electron 39.8.10 的构建，而摆在目录里给人试的 win-unpacked 是 Electron 33.4.11 的构建**。
- **后果**：测 A 产物、发 B 产物，任何"装完和试的不一样"都会变成扯皮；也是用户"有的能跑有的不能跑"观感的来源之一。
- **修复方向**：一次 npm run dist = 一次同源构建；产物文件名/版本资源里带 Electron 与构建时间；构建后断言安装器内 exe 字节数 == win-unpacked 内 exe 字节数。

### [RUN-001] 启动后全部窗口渲染进程启动失败，界面完全不显示（High · 核心功能不可用）

- **现象证据**（%APPDATA%\xiaopeng-toolbox\logs\app.log，两段用户侧真实运行）：
  - 2026-09-29T16:09:02Z（Electron = 39.8.10 / Chromium 142）与 2026-09-30T12:40:11Z（Electron = 33.4.11 / Chromium 130）**同一签名**：
    [watchdog] 渲染进程异常退出（reason=launch-failed，exitCode=18）… / [watchdog] 渲染进程启动失败（launch-failed），不再重载，已隐藏窗口 / [watchdog] 显示前检测到渲染进程已崩溃，先恢复窗口；
  - 同一毫秒级窗口内重复十余次（12:40:11.558 → .792 共 15 次）；
  - 主进程侧一切正常：better-sqlite3 ABI 回退 JSON 后端、watchdog 活性探测已启动、剪贴板监听已启动、托盘已创建、宠物形象解析完成、MCP 服务已启动（http://127.0.0.1:47111/mcp）——**只有渲染进程起不来**。
- **这意味着**：不是"程序崩溃"，而是"主进程活着、每个窗口都画不出来"，用户看到的正是"打开就崩/不显示"，托盘图标还在。
- **已排除的候选（kill-test）**：
  1. **Electron 版本回归**（39 引入）→ 排除：33.4.11 与 39.8.10 两次都复现同一签名。诊断脚本 诊断-小鹏工具箱启动.ps1:69 的旧结论（"A 失败但 D 成功 → 确认是 electron 39 的问题"）**被证伪**；
  2. **运行时文件不完整** → 排除：dist/win-unpacked 与 node_modules/electron/dist 做逐文件名+字节数 diff，差异仅 LICENSE 改名（LICENSE.electron.txt）、version 文件、resources/default_app.asar、主 exe 改名，**全部 DLL/pak/dat/bin 齐全**；
  3. **目录 ACL 缺失（ALL APPLICATION PACKAGES）导致沙箱子进程无法创建** → 排除：icacls 对比 小鹏工具箱.exe 与 node_modules/electron/dist/electron.exe，ACE 集合**完全一致**（含同一异常 SID 与 Low Mandatory Level 标签），两者无差异，不可能是差异因素；
  4. **第三方杀软拦截** → 未发现：本机仅 Windows Defender（Running），Smart App Control 的 VerifiedAndReputablePolicyState=0（关闭），未见第三方 AV 注册项。但 Defender 的「受控文件夹访问/Exploit Protection」配置本沙箱读不到（Get-MpPreference 空输出），**【待验证】**。
- **环境异常（旁证，因果未定）**：两次失败时环境快照均带 __COMPAT_LAYER = DetectorsAppHealth DetectorsAdminProtection Installer（审计环境同变量为空），说明该进程被 Windows 的"安装程序/管理员检测"兼容层包裹——这正是 windowWatchdog.ts:126-130 注释所说的"根因几乎总在系统侧（进程创建被策略拦住、依赖 DLL 解析失败、沙箱初始化失败）"的典型形态。
- **【待验证】最终真因**：需要在用户桌面用 XP_RENDER_DEBUG=1 重启一次，取 logs/chromium.log（electron/main.ts:231-235 已实现该通道，windowWatchdog.ts:149 也提示了），那里面才有 Chromium 自己给出的失败原因。
- **自查**：（1）考虑过"是不是我沙箱里的假象"——两次失败日志的时间戳（本机 00:09 与 20:40）与路径（dist/win-unpacked）来自用户侧运行，且本沙箱连进程都起不来（本次动态启动零日志、进程 0），日志不是我制造的；（2）考虑过"主进程把窗口建在了屏幕外/透明窗"——反驳：那是"幽灵窗口"型缺陷（上轮已析），而本症状是 render-process-gone launch-failed，渲染进程**从未启动**，性质不同。

### [UX-001] 自救路径断裂：兜底只在开发机脚本里，提示指向坏安装包（Medium）

- **证据**：
  - electron/main.ts:94-97 的 XP_NO_SANDBOX 兜底（关 Chromium 沙箱）只认环境变量，产品内无任何入口；
  - 唯一的用户侧兜底是项目根的 启动-兼容模式(关沙箱).bat:16，其内容是 start "" "D:\mimo小鹏工具箱\dist\win-unpacked\小鹏工具箱.exe" —— **硬编码开发机绝对路径**，最终用户既没有这个 .bat，路径也对不上；
  - 崩溃提示 LAUNCH_FAILED_HINT（electron/services/windowWatchdog.ts:116-118）让用户"从安装包安装后的目录运行而不是从解压目录运行"——而安装包正是 PKG-001 的坏产物，这条自救路是死的；
  - 通知侧还被节流：windowWatchdog.ts:94 规定"已隐藏窗口"类通知一个进程最多 2 次，:83-84 在 Notification.isSupported() 为假时静默返回——首启全窗失败时用户可能连一条提示都看不到。
- **后果**：一个本可绕过的环境问题（关沙箱即用），最终表现成"软件坏了、没法用、也没人告诉我怎么办"。

### [SEC-R01] 分发物零签名 + 不编辑 exe 资源（Medium · 发布面）

- **证据**：electron-builder.yml:45 signAndEditExecutable: false（注释自述为绕过 winCodeSign 下载）→ 产物 小鹏工具箱.exe 与 electron.exe **字节数完全相同（188,784,128B）**，即未做 rcedit（无版本资源/无图标）也未做任何 Authenticode 签名。
- **后果**：SmartScreen/Defender/PCA 对"无版本资源+无签名+名字不常见"的 exe 判定最不友好，与 RUN-001 环境快照里的 Installer/DetectorsAdminProtection 兼容层互相印证【因果待验证】；用户也无法校验下载来源。
- **修复方向**：恢复资源编辑 + 代码签名（R2-T5）；至少先把版本资源与图标打回去。

## 四、P1 功能缺陷与健壮性

### [DEF-R01] 启动期 launch-failed 会反复创建渲染进程，无熔断（Medium）

- **证据**：app.log 2026-09-30T12:40:11.558Z→.792Z 共 15 次 render-process-gone(launch-failed)，其间夹着「显示前检测到渲染进程已崩溃，先恢复窗口」与「已隐藏窗口」交替出现。
- **推理**：windowWatchdog.ts:111-114 明确承认"启动失败 reload 一万次也起不来"，通知侧做了双重限流（:77-100），但**恢复动作本身没有熔断**：显示入口的"显示前 isCrashed 自检"仍会再次建窗，于是每个显示动作都撞一次墙。日志里 250ms 内 15 次进程创建失败属于可避免的浪费与刷屏。
- **自查**：考虑过"15 次其实是 15 个不同窗口各自的首启失败"——部分成立（多窗并发创建），但日志中同一窗口标题（xiaopeng-toolbox）反复出现，且伴随"先恢复窗口"字样，说明重建路径确实在重复触发；**具体由哪条创建路径驱动未逐行核实**，机制细节【待验证】，但"无熔断"本身由日志坐实。
- **修复方向**：launch-failed 后进入进程级熔断态（本进程内不再新建渲染进程），统一走 UX-001 的对话框自救。
