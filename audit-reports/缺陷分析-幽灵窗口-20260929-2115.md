## 二、逐条分析

### [GW-01] 窗口看门狗只覆盖「渲染进程崩溃」，不覆盖「停止绘制/冻结」类幽灵
- **严重度**：High
- **位置**：electron/services/windowWatchdog.ts:56（唯一自动恢复触发器 render-process-gone）、:99（did-fail-load）、:152-157（手动逃生口排除截图遮罩）
- **证据**：
  - 看门狗的设计前提写在注释里（windowWatchdog.ts:8-12）：**透明+无边框+置顶窗在渲染进程崩溃后依然可见、依然接收鼠标事件，但什么都不画** —— 这正是用户症状①。
  - 但自动恢复只挂了 `render-process-gone`（56 行）与 `did-fail-load`（99 行）两类事件；**渲染进程没死、只是停止合成/停止绘制**（GPU 进程崩溃、遮挡误判、合成器冻结）时这两个事件都不触发，窗口就永久留在“看不见却挡点击”状态。
  - **用户日志反证（关键）**：09-22 → 09-28 一周内日志里 `[watchdog]` 只出现 2 次（其中 render-process-gone 仅 1 次：09-28 10:58:13 收纳盒），而用户 09-23 14:44:48 主动使用托盘「修复卡住的窗口」：
    ```
    [2026-09-23T14:44:48.743Z] [WARN] [watchdog] 已修复/重载 6 个窗口：桌面工作台、收纳盒、收纳盒、收纳盒、收纳盒、小鹏宠物
    ```
    幽灵**频繁发生**而看门狗**没有记录崩溃** → 触发机制不是“渲染崩溃”，而是看门狗覆盖不到的那类状态。
- **自查**：（1）考虑过“是不是幽灵时看门狗恰好没记录”——不可能：render-process-gone 是必触发事件，日志记录了唯一一次崩溃（10:58），其余幽灵无日志，是“无事件可响应”而非“漏记”；（2）考虑过 repairStuckWindows 能否兜住——它明确跳过截图遮罩/贴图等瞬态窗（157 行注释），且 RELOADABLE_TITLES（29 行）不含“截图/贴图/取色”，兜不住最大的一块遮罩（见 GW-03）；（3）考虑过是否是我读漏了别的恢复路径——grep `webContents.on` 在 windowWatchdog 全文件仅 render-process-gone/did-fail-load 两处。
- **修复方向**：
  1. 补 `app.on('gpu-process-gone')` 与 `win.webContents.on('unresponsive')` 的处理（unresponsive → reload/hide）。
  2. 增加**周期性活性探测**（如每 30s 对可见常驻窗 `capturePage()` 采样哈希/非透明像素比，连续 N 次相同且已知动画在跑 → 判冻结并 reload）。
  3. 逃生口扩到截图遮罩：至少提供“强杀所有截图会话”托盘项（closeOverlay + endCapture）。

### [GW-02] 未禁用 Chromium 原生遮挡计算，后台节流默认开启 —— 透明置顶窗被误判遮挡即冻结但仍吃点击
- **严重度**：High（机制与 GW-01 同源，触发条件为 GPU/遮挡状态）
- **位置**：electron/ 全目录（`grep appendSwitch|commandLine` **零命中**）；electron/services/perf.ts:45；electron/services/perf.ts:31-33
- **证据**：
  - 项目从不设置任何 `app.commandLine.appendSwitch`，包括 Windows 上规避遮挡误判的 `disable-features=CalculateNativeWinOcclusion`。
  - perf.ts:45 对每个窗口 `win.webContents.setBackgroundThrottling(eff.idleRelease)`，而均衡/节省/自定义三档的 idleRelease 都是 true（31-33 行）→ 允许 Chromium 对“被判定为后台/被遮挡”的窗口停帧、停定时器、冻结 IPC。
  - 项目自己实测记录了这个冻结（deskboardWindow.ts:163-165）：“窗口一旦 hide()，其渲染进程立刻被后台节流/冻结，渲染端后续的 IPC 会发不出去”。同一机制作用于“**可见但被误判为被遮挡**”的窗口时，表现就是：什么都不画 + 仍然接受命中测试。
  - 本应用常态是 4-6 个透明置顶窗互相重叠（工作台 1180x680 + 侧边栏 412x840 + 宠物 + 收纳盒 + 贴图），正是 Windows 原生遮挡计算最易误判的形态。
- **自查**：（1）考虑过遮挡计算只影响“完全被盖住”的窗口——不是：Windows 对分层/透明窗的可见性判定基于 DWM 合成结果，透明窗互相覆盖时判定本就不稳，这正是 Chromium 该特性在 Electron 社区长期被要求默认关闭的原因；（2）考虑过 setBackgroundThrottling(true) 是省内存的有意设计——是（perf.ts:10 注释），但“可见窗”不该被节流，应只对 hide()/minimize 的窗口生效；（3）触发条件（GPU 型号/驱动/Win11 26200）未在本沙箱实测复现，标注**待验证**，但禁用遮挡计算 + 仅对隐藏窗节流是无副作用的加固。
- **修复方向**：
  1. main.ts 早期加 `app.commandLine.appendSwitch('disable-features', 'CalculateNativeWinOcclusion')`（一行）。
  2. perf.ts 的 applyIdleFor 改为：仅当 `win.isMinimized() || !win.isVisible()` 时才 setBackgroundThrottling(true)，可见即 false。
  3. 配套实验：跑第五节的 run-ghost-probe.ps1（含 occluded 阶段）对比开关前后帧率。

### [GW-03] 全屏截图遮罩只靠渲染层 IPC 销毁，且无逃生口 —— 渲染一卡就是“整屏点不动”
- **严重度**：High
- **位置**：electron/windows/captureWindows.ts:22-35（virtualBounds=全部显示器并集）、:41-61（screen-saver 级全屏透明遮罩）；electron/services/captureManager.ts:121-127（show）；销毁点仅 electron/ipc/captureIpc.ts:31（`capture:cancel`）与 captureManager.ts:161/190；electron/services/windowWatchdog.ts:157（修复入口明确跳过）
- **证据**：
  - 遮罩覆盖**所有显示器的虚拟桌面**（captureWindows.ts:22-35 + 44-46），层级 `screen-saver`（61 行）压过一切置顶窗。
  - 它的两条退出路径全部依赖**遮罩自己的渲染层**发 IPC（preload.ts:332 `cancel: () => send('capture:cancel')`）；渲染层一旦冻结/崩溃，ESC 和点击都送不进去 → 遮罩永久滞留。
  - 崩溃后的看门狗行为只会 reload（windowWatchdog.ts:88），而重载后的 capture 页**收不到 surfaces**（`once('did-finish-load')` 在 captureManager.ts:122 已消费完），是个无会话的空遮罩；连续崩溃 3 次会被 hide，但**冻结态走不到这里**。
  - 托盘「修复卡住的窗口」跳过它（windowWatchdog.ts:157 注释：跳过瞬态窗口（截图遮罩/贴图等）；RELOADABLE_TITLES（29 行）也不含“截图”）→ 用户无自救手段，只能重启应用。
- **自查**：（1）考虑过 ESC 能否兜底——ESC 由遮罩渲染层处理，渲染冻结时无效，排除；（2）考虑过 beginCapture 互斥/120s 兜底能否救——那只释放会话锁（captureManager.ts:52），销毁不了遮罩窗口，排除；（3）考虑过这是否真能造成“整屏点不动”——遮罩是全虚拟桌面 + screen-saver 层 + 无 setIgnoreMouseEvents（全仓 grep 零命中），滞留即整屏吞点击，成立。
- **修复方向**：
  1. 主进程给遮罩挂**主进程侧兜底**：`win.webContents.on('render-process-gone'|'unresponsive')` → 直接 `closeOverlay()`（不要 reload）。
  2. 遮罩超时自杀：无鼠标活动 N 分钟自动 closeOverlay（或最迟 beginCapture 的 120s 兜底里顺带 closeOverlay）。
  3. 托盘/热键提供「退出截图」全局逃生（主进程直接 closeOverlay + endCapture）。

### [GW-04] 全局热键注册失败静默无提示 —— “按快捷键没窗口”实锤
- **严重度**：High（直接命中症状②，且用户日志已实锤）
- **位置**：electron/services/hotkeyManager.ts:38-40（reportHotkey 只存内存）、:97-99（错误只进 hotkeyList，仅设置页可见）；失败点各模块只 logWarn（electron/windows/deskboardWindow.ts:194-195、clipboardWindow.ts:85-86、electron/services/captureManager.ts:310-311,326-327）
- **证据（用户日志）**：
  ```
  [2026-09-22T15:22:40.148Z] [WARN] [palette] 热键注册失败（可能被其他程序占用）: Alt+Space
  ……（09-22 / 09-23 / 09-27 多次重复）
  [2026-09-27T11:19:29.435Z] [WARN] [palette] 热键 Alt+Space 与 Windows 系统菜单冲突且注册失败，已自动升级为 Ctrl+Space（可在 设置 → 快捷键 更改）
  ```
  即：**至少 5 天里命令面板按快捷键完全呼不出来，用户只能感到“无窗口显示”，没有任何提示**。注册失败时除日志外无任何用户可见反馈。
- **自查**：（1）考虑过“注册失败=功能入口完全消失”是否夸大——命令面板/截图/剪贴板面板都只能通过热键呼出（paletteWindow 懒创建、无托盘入口），失败即入口消失，成立；（2）考虑过新版本升级逻辑是否已覆盖——只覆盖 palette 的 legacy Alt+Space（shared/hotkeys.ts 的 RETIRED_PALETTE_HOTKEY），其他热键被占用仍只有 logWarn。
- **修复方向**：
  1. 首次注册失败弹一次系统通知（复用 Notification，带“去设置修改”指引）。
  2. 失败的热键自动尝试备选（升级逻辑已有先例），或托盘图标显示小红点。

### [GW-05] 工作台位置只算一次，显示时不校验在屏内 —— “呼出了但屏幕上没有”
- **严重度**：Medium
- **位置**：electron/windows/deskboardWindow.ts:36-41（创建时 `screen.getPrimaryDisplay()` 居中一次）、:100-126（showDeskboard 直接 showInactive/show，不 clamp 到当前显示器工作区）
- **证据**：用户日志证实其环境是多显示器/工作区会变化（同一 sidebar 先后出现 `bounds={"x":576,"y":221,"width":384,...}` 与 `{"x":1124,"y":12,"width":412,"height":840}` 两套工作区）。窗口创建后坐标永不重算：显示器休眠唤醒、拔插、DPI 变化后 `show()` 成功但窗口在已消失的坐标上 → “无窗口显示”。对比：paletteWindow.ts:56-62 与 translateBarWindow.ts:45-49 **每次显示都按光标所在显示器重算**，deskboard 没做。
- **自查**：（1）考虑过 skipTaskbar:false 的任务栏能否找回——能找到缩略图但点开仍在屏幕外，体验仍算“无窗口”；（2）考虑过 Windows 是否会自动搬回可见屏——不会，Electron 不做此校验。
- **修复方向**：showDeskboard 开头按 `screen.getDisplayNearestPoint(cursor).workArea` 校验/夹取 bounds（照抄 paletteWindow.ts:56-62 即可）。

### [GW-06] 长截图控制条关闭泄漏捕获互斥锁 —— 2 分钟内截图全部“无反应”
- **严重度**：Medium
- **位置**：electron/windows/captureWindows.ts:277-279（longWin 'closed' 只清句柄，不 endCapture）；electron/services/captureManager.ts:44-48（busy 时**静默 return**）、:52（120s 兜底）
- **证据**：长截图模式下 `handlePickRegion` 不 endCapture（captureManager.ts:162-167，注释说明沿用会话）；用户若直接关掉控制条窗口（或它被 `capture:self-close` 关闭）而没走 `longStop/longFinish`（268-281 里的 endCapture），captureBusy 保持 true → 此后任何截图入口（热键/命令面板/MCP）都在 `beginCapture()` 静默返回，**无窗口、无提示**，直到 120s 兜底。
- **自查**：考虑过 longStop 是否总能被调用——`capture:long-stop` 由渲染层按钮发（preload 侧），窗口被系统/用户直接关闭时不经过它，成立。
- **修复方向**：longWin 的 'closed' 事件里调 `longStop()` + `closeOverlay()`；`beginCapture()` 失败时发通知而不是纯 logWarn。

### [GW-07] showDeskboard 异步收尾对已隐藏窗口调 focus() —— 隐形窗口持有输入
- **严重度**：Medium（代码缺陷确定；OS 层后果标注【待验证】）
- **位置**：electron/windows/deskboardWindow.ts:116-125
- **证据**：
  ```typescript
  w.showInactive();
  void captureContext({ copyKey: true })
    .then(...)
    .finally(() => {
      if (!w.isDestroyed()) w.focus();   // ← 只判 isDestroyed，不判 isVisible
    });
  ```
  而本应用默认是非常驻模式：失焦即自动收起（deskboardWindow.ts:76-78 → hideDeskboardAfterAction:167-170）。于是“呼出工作台（showInactive，不抢焦点）→ 用户点了别处/目标应用接管（blur→hide）→ 抓取完成回调 focus() 作用在**已隐藏**的窗口”是可达时序。对隐藏 HWND 调 focus 在 Windows 上会使该窗口持有前台/键盘输入而不可见——与症状③“窗口已经隐藏但功能仍然能够被点击/有响应”一致。
- **自查**：（1）考虑过 focus() 是否会把窗口重新 show 出来——Electron 的 focus 不会 show，只改焦点归属，故现象是“看不见但吃输入”而非“窗口又出现”；（2）OS 层行为未在真机复现（本沙箱禁 GUI），**后果标待验证**，但补 `if (w.isVisible())` 守卫是零风险修复。
- **修复方向**：`.finally(() => { if (!w.isDestroyed() && w.isVisible()) w.focus(); })`。

### [GW-08] hide() 后渲染被冻结 —— “收起了但功能还在响应/旧按钮还在”的观感来源
- **严重度**：Medium
- **位置**：electron/services/perf.ts:45；electron/windows/deskboardWindow.ts:163-165（项目自述实测）
- **证据**：deskboardWindow.ts:163-165 明确记录“窗口一旦 hide()，其渲染进程立刻被后台节流/冻结，渲染端后续的 IPC（如 api.sidebar.toggle()）会发不出去（实测日志只见 hideDeskboard、不见 toggle）”。隐藏窗状态停在最后一帧；期间渲染端发起的请求排队/丢失，恢复显示时短暂呈现旧 UI、并可能补发旧交互 → 用户感受为“窗口藏起来了但它的功能还在动/还能点”。日志侧佐证：09-27 11:43:44-11:44:17 有 **6 条** `[deskboard] 窗口被隐藏，调用栈` 连续出现（含 hideDeskboardAfterAction 与 IPC 直调两种来源），说明隐藏/显示高频交替，冻结态反复出现。
- **自查**：考虑过是否只是日志噪声——同一秒内重复 hide 不产生新状态，但它们证明了“隐藏路径高频触发”的环境，冻结窗口是常态而非例外。
- **修复方向**：对常驻交互窗（deskboard/sidebar/palette）在 webPreferences 加 `backgroundThrottling: false`，或按 GW-02 第 2 条只对真正隐藏的窗节流。

### [GW-09] hide→延迟 destroy 与 show 的极端竞态
- **严重度**：Low（待验证）
- **位置**：electron/windows/deskboardWindow.ts:143-150（1.5s 后 `win === w && !w.isVisible()` 才 destroy）与 toggleDeskboard:172-175
- **证据**：销毁定时器只看 isVisible；若 destroy 定时器触发与 showInactive 落在同一事件循环窗口（毫秒级），存在“刚要显示的窗口被销毁”或“销毁后句柄仍被在途 IPC 引用”的可能。
- **自查**：现有守卫（win === w && !isVisible）已挡掉绝大多数时序，仅剩毫秒级窗口，故定 Low。
- **修复方向**：destroy 前再挂一次 `win.on('show')` 取消定时器，或改用引用计数。
